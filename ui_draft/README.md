## Architecture overview

```
┌────────────────────┐      ┌────────────────────┐      ┌────────────────────┐
│     Front end      │      │      Back end      │      │ Data ranking/logic │
│  Flutter / Dart    │ <──> │ Firebase/Firestore │ <──> │  Recommendation    │
│  screens, widgets  │      │  `events` data     │      │                    │
└────────────────────┘      └────────────────────┘      └────────────────────┘
```

Inside the app, data flows in one direction:

```
Firestore `events` collection
        │
        ▼
EventService  ── parses + validates ──►  List<Event>   (typed, canonical category ids)
        │
        ▼
FeedPage (StreamBuilder) ── filters by chip / interests ──► EventCard widgets
                                   ▲
                                   │
                         PreferencesStore (interests, commitment, location)
```

Three design rules keep the layers consistent:

1. **`EngagementCategory.id` is the only category identifier.** Events store a `categoryId`; labels, colors, and icons always come from the category model.
2. **One shared `Event` model.** The UI, the Firestore service, and any future data converters all produce or consume the same class.
3. **Parse at the boundary.** Raw Firestore data is validated and converted to typed objects inside `EventService`. The UI never touches raw maps.

## Engagement categories

The app is organized around six categories. Each was researched for what participation actually requires (registration, age limits, waivers, and so on).

| `CategoryIds` constant | Stored id | Label | Chip label |
|---|---|---|---|
| `civic` | `civic` | Civic Meetings & Public Hearings | Civic |
| `directService` | `direct-service` | Direct-Service Volunteering | Volunteer |
| `neighborhood` | `neighborhood` | Neighborhood Stewardship | Stewardship |
| `causeAction` | `cause-action` | Cause Actions | Causes |
| `localCulture` | `local-culture` | Local Arts & Culture | Culture |
| `mutualAid` | `mutual-aid` | Mutual Aid & Crisis Support | Mutual Aid |

Each `EngagementCategory` also defines a tagline, description, examples, icon, and a color pair.

### Category translation

Data from outside the app (Firestore documents, public APIs) may use informal labels. `categoryIdFromRaw()` in `category.dart` normalizes a raw string (lowercase, `&` becomes `and`, punctuation becomes `-`) and returns a canonical id, or `null` if it isn't recognized.

Examples of accepted input: `Civic`, `civic`, `Volunteer`, `Stewardship`, `Causes`, `Culture`, `Arts & Culture`, `Environment`, `Fundraising`.

Aliases are defined in the `_categoryAliases` map. A few are judgment calls (for example `Environment` maps to Neighborhood Stewardship and `Fundraising` maps to Cause Actions). Review and extend that map as new data sources are added.

## Data model

### `Event` (`models/event.dart`)

| Field | Type | Notes |
|---|---|---|
| `id` | `String` | Firestore document id |
| `categoryId` | `String` | Must be a valid `CategoryIds` value |
| `title` | `String` | |
| `org` | `String` | Organizer; hidden on the card when empty |
| `dateLabel` | `String` | Display text, e.g. `Thu, Sep 24 · 7:00 PM` |
| `startsAt` | `DateTime?` | Used for sorting when available |
| `location` | `String` | Free-text place |
| `distanceLabel` | `String?` | e.g. `0.4 mi`; the card falls back to `location` when null |
| `description` | `String` | Hidden on the card when empty |
| `action` | `String` | Button text such as `RSVP` or `Sign up` |
| `spots` | `int?` | Shows "N spots left" when present |

`Event.category` looks up the full `EngagementCategory` for color, label, and icon.

Default button text when none is provided: Civic → "Add to calendar", Direct-Service → "Sign up", Cause Actions → "Join session", everything else → "RSVP".

### `UserPreferences` (`models/user_preferences.dart`)

| Field | Type | Notes |
|---|---|---|
| `categoryIds` | `Set<String>` | Chosen interests |
| `commitment` | `String?` | `drop-in`, `occasional`, or `regular` |
| `locationLabel` | `String` | Defaults to `Brooklyn, New York` |

`toMap()` is already shaped for storing under a user document later.

## Firestore setup

Events are read from the top-level **`events`** collection.

### Document fields

| Field | Type | Required | Notes |
|---|---|---|---|
| `title` | string | Recommended | Blank becomes "Untitled event" |
| `categoryId` | string | **Yes** (or legacy `category`) | Use the exact stored ids from the table above |
| `category` | string | Legacy alternative | Free text; translated by `categoryIdFromRaw()` |
| `date` | string or timestamp | Optional | Strings are shown as-is; timestamps are formatted and used for sorting |
| `startsAt` | timestamp | Optional | Preferred sort key |
| `location` | string | Optional | |
| `description` | string | Optional | |
| `org` | string | Optional | |
| `action` | string | Optional | Overrides the default button text |
| `spots` | number | Optional | |

### Example document

```json
{
  "title": "Prospect Park Fall Cleanup",
  "categoryId": "neighborhood",
  "org": "Prospect Park Alliance",
  "startsAt": "<Timestamp: 2026-09-28 10:00>",
  "location": "Prospect Park",
  "description": "Seasonal trail and meadow cleanup. Gloves and tools provided.",
  "action": "RSVP",
  "spots": 18
}
```

### `EventService` behavior

- `getEvents()` performs a one-time fetch and returns `List<Event>`.
- `watchEvents()` returns a live stream that emits a new list whenever the collection changes. The feed uses this.
- A document with a missing or unrecognized category is **skipped** and logged with `debugPrint`, rather than crashing the feed. If events seem to be missing, check the debug console.
- Events are sorted soonest first; events without a parseable date go last.

### Security rules

The app only reads from `events`. Make sure Firestore security rules allow reads on that collection and do not allow unauthenticated writes. A `permission-denied` error in the feed's debug output means the rules are blocking reads.

## User preferences and onboarding

### Flow

```
/welcome  ──►  /interests (step 1: pick interests)  ──►  step 2: commitment  ──►  /feed
   │                                                                               ▲
   └──────────────────────────  "Skip for now"  ───────────────────────────────────┘
```

- **Welcome:** the user sets a neighborhood by typing it or tapping "Use my current location" (currently a simulated detection). The label is saved immediately.
- **Interests (step 1):** multi-select over the six categories. The user must pick at least one to continue.
- **Commitment (step 2):** "Drop-in", "Occasional", or "Regular".
- **Finish:** "Find events near me" saves the choices and opens the feed.
- **Editing:** "Edit" on the profile reopens the same screens, pre-filled with the saved choices.
- The step indicator shows two steps. The location step lives on the welcome screen.

### `PreferencesStore` (`services/preferences_store.dart`)

A singleton built on Flutter's `ChangeNotifier`, so no extra state-management package is needed.

- `PreferencesStore.instance.prefs` reads the current preferences.
- `update(prefs)` and `setLocation(label)` change them, notify listeners, and persist to the device.
- `load()` runs once in `main()` before `runApp()`.
- Stored category ids that no longer exist (for example after a rename) are dropped when loading.

Persisted keys: `pref_category_ids`, `pref_commitment`, `pref_location_label`.

When user accounts are added, only `load()` and `update()` need to change to read and write a per-user Firestore document.

## The feed

`FeedPage` streams events from `EventService.watchEvents()`.

- **Chips:** `For you` (only when the user has chosen interests), `All`, then one chip per category, generated from `allCategories` so they can never drift from the model.
- **Default view:** "For you" when interests exist, otherwise "All".
- **States:** a spinner while loading, a friendly message on error (with the technical detail shown in debug builds), and an empty state that explains what to try next.
- **Cards:** category badge, optional "spots left", bookmark toggle, title, organizer, description, date, distance or location, and an action button, all in the category's color.
- **Bookmarks:** tracked by event id, so they stay correct when the filter changes. They are not persisted yet.
- **Header:** shows the saved neighborhood.

## Getting started

### Prerequisites

- Flutter 3.27 or newer (stable) and the Dart SDK that ships with it
- A Firebase project with Cloud Firestore enabled
- Xcode (iOS/macOS) or Android Studio (Android) for device builds

### Setup

```bash
git clone <repository-url>
cd InVolve/ui_draft
flutter pub get
flutter run
```

If `shared_preferences` is not yet in `pubspec.yaml`:

```bash
flutter pub add shared_preferences
```

### Firebase

`firebase_options.dart` and the platform config files are generated by the FlutterFire CLI. To connect your own copy of the project:

```bash
dart pub global activate flutterfire_cli
flutterfire configure
```

### iOS signing

Platform build settings may contain a developer-specific bundle id or Apple team. Set your own signing team in Xcode before building for iOS.

### Sanity check

1. Run `flutter analyze` and fix any errors.
2. Launch the app and go through Welcome, then Interests.
3. Confirm the feed opens on **For you** and shows events from Firestore.
4. Open the **You** tab and confirm your interests and location appear.
5. Fully restart the app and confirm your choices are still saved.

## Known limitations

- **Map:** the Explore tab and the welcome map are static placeholders; `google_maps_flutter` needs an API key and integration.
- **Distance:** cards cannot show real distances yet because events have no coordinates. The location text is shown instead.
- **Location detection:** "Use my current location" is simulated.
- **Saved events:** bookmarks are not persisted, and the Saved tab does not list them yet.
- **Volunteer tab:** uses its own sample data and colors rather than the shared `Event` model.
- **Explore header:** still shows a hardcoded "BROOKLYN, NY".
- **Source coverage:** government meeting data depends on which systems each city uses. Coverage will not be complete outside cities with supported sources.
- **Accounts:** there is no sign-in yet; preferences live on the device only.
- **Sign out:** the button is not wired up.

## Team conventions

- Reference categories through `CategoryIds`, never raw strings.
- Anything that produces events (Firestore, APIs, manual entry) must output a valid `categoryId`.
- Add new fields to `Event` first, then update the Firestore parsing and the UI.
- Work on feature branches and open pull requests into the shared branch. Resolve `pubspec.yaml`, `pubspec.lock`, and `main.dart` conflicts by keeping both sides' changes, then run `flutter pub get` to regenerate the lock file.
- Do not commit personal signing settings or credentials.
